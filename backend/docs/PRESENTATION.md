## 1 · ปัญหาและขอบเขต (1 นาที)

> สวัสดีครับอาจารย์ ผมณัฐดนัยครับ วันนี้จะนำเสนอโปรเจกต์ชื่อ **CS-CloudFlow**
>
> ปัญหาที่ตั้งต้นคือ เวลานักศึกษาต้องการเครื่องเซิร์ฟเวอร์มาทำโปรเจกต์ — เช่นเทรนโมเดล
> หรือทำแล็บฐานข้อมูลแบบกระจาย — ตอนนี้ยังใช้วิธีเดินไปขอ หรือส่งข้อความหาผู้ดูแลระบบ
> ปัญหาคือไม่มีใครตอบได้ว่าตอนนี้เครื่องไหนว่าง ใครใช้อะไรอยู่ และใครเป็นคนอนุมัติให้
>
> ระบบนี้ทำให้กระบวนการนั้นเป็นขั้นตอนที่ตรวจสอบได้ — **นักศึกษายื่นคำขอ อาจารย์รับรอง
> แอดมินจัดเครื่องให้ และทุกการกระทำถูกบันทึกไว้**
>
> ขอบเขตที่ทำเสร็จแล้วมีสามส่วน: ฐานข้อมูล PostgreSQL, REST API บน NestJS
> และหน้าเว็บ Next.js ครับ

## 3 · การออกแบบฐานข้อมูล (3 นาที 30) ⭐

> ฐานข้อมูลออกแบบตาม ER Diagram ที่ได้รับ มี **5 ตาราง** ครับ:
> `users` · `resources` · `requests` · `allocations` · `audit_logs`
> และ 3 enum คือ role ของผู้ใช้ สถานะของเครื่อง และสถานะของคำขอ

### 3.1 ทำไม ON DELETE ของแต่ละความสัมพันธ์ไม่เหมือนกัน

> จุดแรกที่ผมอยากให้ดูคือ foreign key ทั้ง 5 เส้นใช้ `ON DELETE` ไม่เหมือนกันเลย
> ซึ่งไม่ใช่ความไม่สม่ำเสมอ แต่เป็นคำตอบของคำถามว่า *"ถ้าลบของต้นทาง ของปลายทางควรหายด้วยไหม"*
>
> - `users` → `requests` ใช้ **RESTRICT** — ลบผู้ใช้ที่ยังมีคำขอค้างไม่ได้
>   เพราะถ้าลบได้ คำขอจะกลายเป็นของ "ไม่มีใคร" แล้วประวัติการอนุมัติทั้งชุดจะอธิบายไม่ได้
>
> - `requests` → `allocations` ใช้ **CASCADE** — การจัดสรรไม่มีความหมายถ้าไม่มีคำขอ
>   ลบคำขอแล้วการจัดสรรควรหายตามไป
>
> - `users` → `audit_logs` ใช้ **SET NULL** — log ต้องอยู่ต่อแม้ผู้ใช้จะถูกลบ
>   ไม่งั้นการลบบัญชีจะกลายเป็นการลบร่องรอยของตัวเองไปด้วย ซึ่งผิดวัตถุประสงค์ของ audit log

### 3.2 สิ่งที่ตั้งใจ "ไม่เก็บ"

> จุดที่สองที่อยากให้ดูคือ **ตาราง `resources` ไม่มีคอลัมน์ว่าใช้ไปเท่าไหร่**
> เก็บแค่ความจุรวม — `total_cpu`, `total_ram_gb`, `total_storage_gb`
>
> เหตุผลคือ ถ้าเก็บทั้ง `total` และ `used` ไว้คู่กัน วันหนึ่งมันจะไม่ตรงกัน
> อาจจะเพราะเขียนสำเร็จแค่ตัวเดียว หรือมีคนแก้ตรง ๆ ใน pgAdmin
> แล้วพอไม่ตรงกัน เราจะไม่รู้ด้วยซ้ำว่าตัวไหนถูก
>
> ผมเลยใช้ **view ชื่อ `resource_usage`** คำนวณสดจากตาราง `allocations` ทุกครั้งที่เรียก
> ทรัพยากรคงเหลือจึงไม่มีทางไม่ตรงกับความจริง เพราะไม่ได้ถูกเก็บไว้ที่ไหนเลย

### 3.3 สามคอลัมน์ที่เพิ่มจาก ER เดิม

> ER ที่ได้รับผมรักษาไว้ครบทุกคอลัมน์ แต่เพิ่มมา 3 ตัว แต่ละตัวมีเหตุผลเฉพาะครับ
>
> **`released_at` ใน `allocations`** — ตัวนี้สำคัญที่สุด ถ้าไม่มี เราจะตอบไม่ได้ว่า
> port นี้ "ยังถูกใช้อยู่" หรือ "เคยถูกใช้" ทางเลือกคือลบแถวทิ้งตอนคืนเครื่อง
> ซึ่งแปลว่าประวัติการใช้งานหายไปด้วย การทำเครื่องหมายแทนการลบ ทำให้ได้ทั้งสองอย่าง
> เดี๋ยวหัวข้อถัดไปจะเห็นว่าคอลัมน์นี้ทำอะไรได้อีก
>
> **`reviewed_at` ใน `requests`** — แยก "สร้างเมื่อไหร่" ออกจาก "ถูกพิจารณาเมื่อไหร่"
>
> **`updated_at`** ในสามตารางหลัก — ตอบคำถามว่าแก้ล่าสุดเมื่อไหร่โดยไม่ต้องไปงม log

## 4 · กติกาที่ชั้นฐานข้อมูล (2 นาที 30) ⭐

> หัวข้อนี้คือส่วนที่ผมคิดว่าต่างจากงานทั่วไปมากที่สุดครับ
>
> คำถามคือ **validation ควรอยู่ที่ไหน** งานส่วนใหญ่จะตรวจที่ API อย่างเดียว
> แต่การตรวจที่ API ถูก "อ้อม" ได้ — ถ้าใครเปิด pgAdmin แล้ว INSERT ตรง ๆ
> หรือรันสคริปต์ import ที่ลืมเช็ก การตรวจทั้งหมดที่เขียนไว้จะไม่ทำงานเลยสักบรรทัด
>
> ผมเลยวางกติกาที่ "ผิดแล้วข้อมูลพังถาวร" ไว้ที่ฐานข้อมูลด้วย
> อยู่ใน migration ตัวที่สองชื่อ `business_constraints` มี **CHECK 8 ตัว · trigger 3 ตัว ·
> partial unique index 2 ตัว · view 1 ตัว**

### 4.1 ทำไมบางอย่างต้องเป็น trigger ไม่ใช่ CHECK

> เช่นกติกาที่ว่า `student_id` ต้องเป็นผู้ใช้ที่มี role เป็น STUDENT
>
> เขียนเป็น `CHECK` ไม่ได้ครับ เพราะ `CHECK` มองเห็นได้แค่แถวของตัวเอง
> มันอ่าน role จากตาราง `users` ไม่ได้ เงื่อนไขที่ต้องข้ามตารางจึงต้องเป็น trigger

### 4.2 จุดที่ผมอยากให้ดูที่สุด — partial unique index

> อันนี้คือส่วนที่ผมภูมิใจที่สุดครับ เป็นการกัน port ชนกันบนเครื่องเดียวกัน
>
> วิธีที่คนมักเขียนคือ SELECT ดูก่อนว่า port ว่างไหม แล้วค่อย INSERT
> **แต่วิธีนั้นมีรูรั่ว** — ระหว่างสองคำสั่งนั้นมีช่องว่างเวลาอยู่
> ถ้าแอดมินสองคนกดพร้อมกัน ทั้งคู่จะเช็กแล้วเจอว่าว่าง แล้วทั้งคู่ก็ INSERT สำเร็จ
>
> ผมเลยให้ฐานข้อมูลเป็นคนกัน ซึ่งไม่มีช่องว่างให้หลุด:
>
> ```sql
> CREATE UNIQUE INDEX allocations_active_port_uniq
>   ON allocations (resource_id, port)
>   WHERE released_at IS NULL;
> ```
>
> **ท่อน `WHERE` บรรทัดสุดท้ายคือหัวใจ** ถ้าไม่มี port ที่คืนแล้วจะใช้ซ้ำไม่ได้ตลอดกาล
> ซึ่งไม่ตรงกับความจริง เติมเข้าไป กติกาจึงกลายเป็น *"ห้ามซ้ำเฉพาะตอนที่ยังใช้อยู่"*
>
> และนี่คือเหตุผลที่ต้องมีคอลัมน์ `released_at` ที่พูดถึงเมื่อกี้ครับ

### 4.3 audit_logs เขียนได้อย่างเดียว

> อีกตัวคือ trigger ที่ห้าม UPDATE และ DELETE บนตาราง `audit_logs`
> เพราะบันทึกที่แก้ย้อนหลังได้ ไม่ใช่บันทึกการตรวจสอบ — มันเป็นแค่ตารางธรรมดาที่ตั้งชื่อว่า audit

## 5 · ความปลอดภัยของ API (1 นาที 30)

> ฝั่ง API มี 4 เรื่องที่ตั้งใจออกแบบครับ
>
> **หนึ่ง — ตัวตนมาจาก token เสมอ ไม่เคยมาจาก body**
> ตอนนักศึกษายื่นคำขอ `studentId` ถูกอ่านจาก token ถ้ารับจาก body จะยื่นคำขอในนามคนอื่นได้
>
> **สอง — ยัดฟิลด์เกินมาแล้วถูกตีตก** ผมเปิด `forbidNonWhitelisted`
> ถ้าส่ง `"status": "APPROVED"` แนบมาด้วย จะได้ 400 พร้อมบอกว่าคีย์ไหนเกิน
> ไม่ใช่เงียบ ๆ ตัดทิ้งแบบที่หลาย framework ทำเป็นค่าเริ่มต้น เพราะแบบนั้นคนยิงจะเข้าใจผิดว่าค่าถูกใช้แล้ว
>
> **สาม — ของคนอื่นตอบ 404 ไม่ใช่ 403**
> ถ้านักศึกษาคนอื่นเปิดคำขอของเรา ระบบตอบว่า "ไม่พบ"
> เพราะ 403 แปลว่า "ของชิ้นนี้มีอยู่จริงแต่คุณไม่มีสิทธิ์" ซึ่งพอให้ไล่ยิง id ทีละเลข
> จนรู้ว่าระบบมีคำขอเลขไหนบ้างและมีทั้งหมดกี่ใบ
>
> **สี่ — role ถูกอ่านจากฐานข้อมูลใหม่ทุก request** ไม่ได้เชื่อ role ที่ฝังอยู่ใน token
> ถ้าเชื่อ คนที่เพิ่งถูกลดสิทธิ์จะยังใช้สิทธิ์เดิมได้จนกว่า token ใบเก่าจะหมดอายุ ซึ่งคือ 8 ชั่วโมง

## 6 · การทดสอบ (2 นาที)

> ส่วนการทดสอบมีสองชุดครับ
>
> **ชุดแรกคือ Postman — 96 request 167 assertion ผ่านหมด ไม่มีข้อแดง**
>
> แต่ตัวเลขที่ผมอยากให้ดูจริง ๆ คือ **จาก 96 ข้อ มี 40 ข้อที่ตั้งใจให้ error**
> เพราะ API ที่ "ใช้ได้" แต่ปล่อยให้ใครก็แก้ข้อมูลของคนอื่นได้ คือ API ที่พัง —
> แค่พังในทางที่ไม่มีใครเห็นตอนเดโม
>
> ตัวอย่างข้อที่เป็นคู่กัน: ข้อ 6.8 ทดสอบว่า port ซ้ำตอนยังใช้อยู่ต้องได้ 409
> และข้อ 6.17 ทดสอบว่า port เดิม**หลังคืนเครื่องแล้ว**ต้องใช้ซ้ำได้ ได้ 201
> ถ้ามีแค่ข้อแรก เราจะไม่มีทางรู้เลยว่า index เขียนผิดเป็นแบบห้ามซ้ำตลอดกาล
>
> **ชุดที่สองคือยิง SQL ตรง ไม่ผ่าน API เลย 12 ข้อ** อยู่ในไฟล์ `scripts/db-rules-check.sql`
> ทุกข้อต้องขึ้น ERROR และขึ้นครบทุกข้อ — เป็นการพิสูจน์ว่าต่อให้อ้อม API ไป
> กติกาก็ยังทำงาน เช่นลอง UPDATE บน `audit_logs` ตรง ๆ ก็ยังถูกปฏิเสธ

> อ้างอิง: `RUN-LOG.md` §2 และ §3 มีผลรันจริงทั้งสองชุด · `TEST-GUIDE.md` อธิบายรายข้อ

## 8 · สรุปและงานที่เหลือ (1 นาที)

> สรุปครับ สิ่งที่ผมคิดว่าเป็นจุดเด่นของงานนี้มี 3 อย่าง
>
> **หนึ่ง** กติกาสำคัญถูกบังคับที่ชั้นฐานข้อมูล ไม่ใช่แค่ที่โค้ด
>
> **สอง** ทรัพยากรคงเหลือคำนวณสด ไม่เก็บซ้ำ จึงไม่มีทางไม่ตรงกัน
>
> **สาม** ชุดทดสอบเกือบครึ่งเป็นการทดสอบว่า "ทำสิ่งที่ไม่ควรทำได้ไม่ได้จริง"
>
> ส่วนที่ยังไม่ได้ทำและรู้ตัวว่ายังขาดมี 4 อย่างครับ:
>
> - งานอัตโนมัติเปลี่ยนคำขอที่เลยกำหนดเป็น EXPIRED — ตอนนี้เปลี่ยนตอนแอดมินกดคืนเครื่องเท่านั้น
> - rate limit ที่หน้า login — ตอนนี้ยิงเดารหัสผ่านได้ไม่จำกัดจำนวนครั้ง
> - unit test ฝั่งโค้ด — ตอนนี้ทดสอบผ่าน Postman ซึ่งครอบพฤติกรรมแต่ไม่ครอบ edge case ในฟังก์ชันย่อย
> - อีเมลแจ้งเตือนตอนคำขอถูกอนุมัติหรือปฏิเสธ
>
> จบการนำเสนอครับ ยินดีรับคำถามครับ

# คำถามที่น่าจะโดนถาม พร้อมคำตอบ

> ซ้อมส่วนนี้ให้ดีกว่าสคริปต์หลัก — คะแนนส่วนใหญ่อยู่ที่ตอบคำถามได้

### ❓ "ทำไมไม่ใช้ MongoDB / ทำไมต้อง PostgreSQL"

> ข้อมูลของระบบนี้มีความสัมพันธ์ชัดเจนและต้องคงความถูกต้องข้ามตาราง เช่น
> การจัดสรรต้องผูกกับคำขอที่อนุมัติแล้วเท่านั้น งานแบบนี้ได้ประโยชน์จาก foreign key,
> transaction และ constraint ซึ่งเป็นของที่ relational database ให้มาฟรี
> ถ้าใช้ document database ผมต้องเขียนตรรกะพวกนี้เองทั้งหมดในโค้ด และมันจะถูกอ้อมได้

### ❓ "trigger ทำให้ช้าลงไหม"

> trigger ที่ใช้เป็นแบบ BEFORE INSERT/UPDATE และอ่านแค่แถวเดียวผ่าน primary key
> ต้นทุนจึงต่ำมาก จากการรันชุดทดสอบ 96 request เวลาตอบเฉลี่ยอยู่ที่ประมาณ 17–18 มิลลิวินาที
>
> และผมมองว่าเป็นการแลกที่คุ้ม — เพราะถ้าย้ายไปตรวจในโค้ดอย่างเดียว
> มันจะถูกข้ามได้ทุกครั้งที่มีใครเข้าฐานข้อมูลตรง ๆ

### ❓ "ทำไมตรวจซ้ำสองที่ ไม่ซ้ำซ้อนเหรอ"

> ตั้งใจให้ซ้ำครับ แต่คนละหน้าที่กัน
> ที่ API ตรวจเพื่อ**ให้ข้อความที่อ่านรู้เรื่อง** — บอกได้ว่าฟิลด์ไหนผิดและควรแก้ยังไง
> ที่ฐานข้อมูลตรวจเพื่อ**ไม่ให้ข้อมูลพังไม่ว่าจะเข้าทางไหน**
>
> ถ้ามีแค่ที่ API ข้อมูลพังได้ ถ้ามีแค่ที่ฐานข้อมูล ผู้ใช้จะได้ข้อความ error ดิบ ๆ ที่อ่านไม่รู้เรื่อง

### ❓ "ถ้าคนสองคนกดจัดสรรเครื่องเดียวกัน port เดียวกันพร้อมกันจะเป็นยังไง"

> คนหนึ่งจะสำเร็จ อีกคนจะได้ 409 ครับ เพราะการกันอยู่ที่ unique index
> ซึ่งฐานข้อมูลรับประกันความถูกต้องให้ ไม่ใช่การเช็กในโค้ดที่มีช่องว่างระหว่าง SELECT กับ INSERT
>
> และการสร้าง allocation ทั้งหมดอยู่ใน transaction เดียว ถ้าขั้นไหนพังจะย้อนกลับหมด
> จึงไม่มีทางเกิดคำขอที่สถานะเป็น ALLOCATED โดยไม่มีเครื่องจริง

### ❓ "ทำไมไม่ลบแถวตอนคืนเครื่อง"

> เพราะจะทำให้ประวัติการใช้งานหายครับ ถ้าลบทิ้ง เราจะตอบไม่ได้ว่าใครเคยใช้เครื่องไหนช่วงไหน
> การประทับ `released_at` แทน ทำให้ port กลับมาใช้ได้และประวัติยังอยู่พร้อมกัน

### ❓ "ทดสอบเองแล้วมันก็ต้องผ่านสิ"

> ครับ ผมเลยเขียนให้เกือบครึ่งของชุดทดสอบเป็นการทดสอบว่า**ระบบต้องปฏิเสธ**
> 40 จาก 96 ข้อคาดหวัง error และมีชุดที่ยิง SQL ตรงอ้อม API ไปเลยอีก 12 ข้อ
>
> ระหว่างพัฒนาชุดทดสอบจับบั๊กจริงได้หลายตัวด้วยครับ เช่นตอนคืนเครื่อง
> สถานะคำขอยังเป็น ALLOCATED อยู่ทั้งที่ควรเป็น EXPIRED เพราะในทรานแซกชัน
> ผมอัปเดต allocation ก่อนปิดคำขอ ค่าที่ดึงกลับมาเลยเป็นภาพเก่า — บันทึกไว้ใน `RUN-LOG.md` §5

### ❓ "เพดานโควตาในหน้าเว็บบังคับจริงไหม"

> **ไม่ครับ** แถบ Quota Impact กับ `Active Quota` เป็นค่าที่ตั้งไว้ฝั่งหน้าเว็บเพื่อช่วยผู้ขอกะขนาด
> ยิงผ่าน Postman ข้ามได้ ถ้าจะให้บังคับจริงต้องเพิ่มการตรวจใน `RequestsService`
> ผมเขียนแยกไว้ชัดใน `FRONTEND.md` ว่าตัวเลขไหนมาจากฐานข้อมูลจริง ตัวไหนเป็นค่าที่ตั้งเอง

### ❓ "ถ้าจะขยายให้รองรับหลายคณะ ต้องแก้อะไร"

> เพิ่มตาราง `departments` แล้วให้ `users` กับ `resources` อ้างถึง จากนั้นเติมเงื่อนไขกรองตามคณะ
> ในชั้นที่กำหนดขอบเขตการมองเห็น ซึ่งรวมอยู่ที่เดียวคือเมธอด `scopeFor` ใน `RequestsService`
> ตรงนั้นเป็นจุดเดียวที่ตัดสินว่าใครเห็นอะไร จึงแก้ที่เดียวได้

### ❓ "ทำไม audit_logs ต้องห้ามแก้"

> เพราะจุดประสงค์ของมันคือใช้ตรวจสอบย้อนหลัง ถ้าแก้ได้ หลักฐานก็ไม่ใช่หลักฐาน
> ผมเลยใส่ trigger ปฏิเสธ UPDATE และ DELETE ไว้ที่ตัวตาราง ไม่ใช่แค่ไม่เปิด endpoint ให้
> เพราะการไม่เปิด endpoint กันได้แค่คนที่เข้าทาง API
