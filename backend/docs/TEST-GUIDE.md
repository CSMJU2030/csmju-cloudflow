## แนวคิดของชุดทดสอบนี้

ชุดทดสอบส่วนใหญ่เช็กแค่ว่า "ทำงานได้ไหม" ชุดนี้แบ่งเป็นสองแบบพอ ๆ กัน:

| แบบ | ถามว่า | ตัวอย่าง |
|---|---|---|
| **ทางสว่าง** (happy path) | ทำสิ่งที่ควรทำได้ ได้จริงไหม | นักศึกษายื่นคำขอ → `201` |
| **ทางมืด** (negative path) | ทำสิ่งที่ไม่ควรทำได้ **ไม่ได้จริงไหม** | นักศึกษากดอนุมัติคำขอตัวเอง → `403` |

จาก 96 ข้อ มี **40 ข้อที่คาดหวัง error** โดยตั้งใจ เพราะ API ที่ "ใช้ได้" แต่ปล่อยให้ใครก็แก้ข้อมูลของคนอื่นได้
คือ API ที่พัง — แค่พังในทางที่ไม่มีใครเห็นตอนเดโม

## 2 · Auth — 16 ข้อ

รากฐานของทุกอย่าง — ถ้าตัวตนของผู้ยิงเชื่อถือไม่ได้ การตรวจสิทธิ์ที่เหลือก็ไม่มีความหมาย
โฟลเดอร์นี้ยัง **เก็บ token ของทุก role ไว้ให้โฟลเดอร์อื่นใช้** ด้วย

### ล็อกอินเก็บ token (2.1–2.5)

| ข้อ | ใคร | เก็บไว้ทำอะไรต่อ |
|---|---|---|
| 2.1 | ADMIN | จัดการเครื่อง · จัดสรร · อ่าน audit log |
| 2.2 | TEACHER (อ.สมชาย) | อนุมัติ/ปฏิเสธคำขอ |
| 2.3 | TEACHER คนที่สอง (อ.วนิดา) | **ทดสอบว่าอาจารย์คนอื่นอนุมัติแทนกันไม่ได้** (ข้อ 5.11) |
| 2.4 | STUDENT (ณัฐดนัย) | ผู้ขอหลัก |
| 2.5 | STUDENT คนที่สอง (ปิยะ) | **คู่ทดสอบว่าเปิดคำขอของคนอื่นไม่ได้** (ข้อ 5.9) |

ทุกข้อเช็กเหมือนกัน 3 อย่าง: ได้ `accessToken` · `role` ถูกต้อง · **ผลลัพธ์ไม่มีคำว่า `passwordHash` หลุดออกมา**

### ทางมืดของการล็อกอิน (2.6–2.7)

| ข้อ | ยิงอะไร | ทดสอบว่า |
|---|---|---|
| 2.6 | รหัสผ่านผิด | ตอบ `401 CREDENTIALS_INVALID` |
| 2.7 | อีเมลที่ไม่มีในระบบ | ตอบ **ข้อความเดียวกับ 2.6 เป๊ะ** |

คู่นี้สำคัญกว่าที่ดู — ถ้าสองกรณีตอบต่างกัน (เช่น "ไม่พบผู้ใช้" กับ "รหัสผ่านผิด")
คนไม่หวังดีจะยิงรายชื่ออีเมลทีละอันเพื่อดูว่าอันไหนมีบัญชีจริง เรียกว่า *user enumeration*

โค้ดยังเทียบ bcrypt ทิ้งเปล่า ๆ แม้ไม่พบผู้ใช้ เพื่อให้**เวลาที่ใช้ตอบใกล้เคียงกัน**ด้วย

### สมัครสมาชิก (2.8–2.10)

| ข้อ | ยิงอะไร | ทดสอบว่า | ต้องได้ |
|---|---|---|---|
| 2.8 | สมัครนักศึกษาใหม่ | role ถูกบังคับเป็น `STUDENT` เสมอ — ยัด `role: "ADMIN"` มาก็ไม่มีผล | `201` |
| 2.9 | อีเมลซ้ำ | unique index ที่ `users.email` ทำงาน | `409 DUPLICATE` |
| 2.10 | รหัสผ่าน `123` | บังคับความยาวขั้นต่ำ 8 ตัว | `400` |

> ใช้ timestamp ต่อท้ายอีเมลกับรหัสนักศึกษา จึงรันซ้ำได้ไม่ชนของเดิม

### token (2.11–2.13)

| ข้อ | ยิงอะไร | ต้องได้ |
|---|---|---|
| 2.11 | `GET /auth/me` พร้อม token | `200` · เป็นคนเดียวกับที่ล็อกอิน · ไม่มี `passwordHash` |
| 2.12 | ไม่แนบ header `Authorization` เลย | `401 TOKEN_MISSING` |
| 2.13 | แนบ token มั่ว `aaaa.bbbb.cccc` | `401 TOKEN_INVALID` |

แยกสองรหัสเพื่อให้ debug ง่าย — "ลืมใส่" กับ "ใส่แล้วแต่ใช้ไม่ได้" คนละปัญหากัน

> ค่า `badToken` ต้องเป็นตัวอักษร ASCII เท่านั้น เคยลองใส่ภาษาไทยแล้วส่งไม่ออก เพราะ HTTP header รับแต่ ASCII

### เปลี่ยนรหัสผ่าน (2.14–2.16)

| ข้อ | ยิงอะไร | ทดสอบว่า |
|---|---|---|
| 2.14 | ใส่รหัสเดิมผิด | `401` — เปลี่ยนรหัสคนอื่นด้วย token ที่ขโมยมาอย่างเดียวไม่ได้ ต้องรู้รหัสเดิมด้วย |
| 2.15 | ใส่รหัสเดิมถูก | `200` |
| 2.16 | ล็อกอินด้วยรหัส**ใหม่** | `200` — พิสูจน์ว่า hash ถูกเขียนทับจริง ไม่ใช่แค่ตอบ 200 เฉย ๆ |

ข้อ 2.16 คือหัวใจ — ถ้ามีแค่ 2.15 เราจะรู้แค่ว่า API ตอบ 200 ไม่รู้ว่ามันทำอะไรจริงหรือเปล่า

## 3 · Users — 11 ข้อ

| ข้อ | ยิงอะไร | ทดสอบว่า | ต้องได้ |
|---|---|---|---|
| 3.1 | `GET /users/teachers` ด้วย token นักศึกษา | นักศึกษาต้องเรียกได้ เพราะต้องเลือกอาจารย์ตอนยื่นคำขอ · ไม่มี `passwordHash` | `200` |
| 3.2 | `GET /users` ด้วย token ADMIN | ดูรายชื่อทั้งหมดได้ · มี `meta` สำหรับแบ่งหน้า | `200` |
| 3.3 | `GET /users` ด้วย token นักศึกษา | **นักศึกษาดูรายชื่อผู้ใช้ทั้งระบบไม่ได้** | `403 ROLE_FORBIDDEN` |
| 3.4 | `?role=TEACHER` | ตัวกรองทำงาน — ทุกแถวที่ได้ต้องเป็น TEACHER | `200` |
| 3.5 | `?role=SUPERUSER` | ค่าที่ไม่มีใน enum ถูกตีตก ไม่ใช่เงียบ ๆ คืนทั้งหมด | `400` |
| 3.6 | ADMIN สร้าง TEACHER | สร้าง role สูงได้เฉพาะ ADMIN · `studentCode` เป็น `null` | `201` |
| 3.7 | สร้าง STUDENT ไม่ใส่ `studentCode` | นักศึกษาต้องมีรหัสนักศึกษา | `400 STUDENT_CODE_REQUIRED` |
| 3.8 | สร้าง TEACHER พร้อม `studentCode` | อาจารย์ต้องไม่มีรหัสนักศึกษา | `400 STUDENT_CODE_NOT_ALLOWED` |
| 3.9 | แก้ชื่อผู้ใช้ที่เพิ่งสร้าง | `PATCH` ทำงาน และค่าเปลี่ยนจริง | `200` |
| 3.10 | ADMIN ลบบัญชี**ตัวเอง** | กันเผลอลบจนไม่เหลือแอดมิน | `409 SELF_DELETE` |
| 3.11 | ลบ id `999999` | ไม่พบต้องตอบ 404 ไม่ใช่พังเป็น 500 | `404` |

ข้อ 3.7 กับ 3.8 เป็นคู่กัน — บังคับกติกาทั้ง**สองทาง** ไม่ใช่แค่ทางเดียว
ชุดทดสอบที่เช็กแค่ "ขาดแล้วต้อง error" มักปล่อยให้ "เกินมาแล้วผ่าน" หลุดไป

## 4 · Resources — 9 ข้อ

| ข้อ | ยิงอะไร | ทดสอบว่า | ต้องได้ |
|---|---|---|---|
| 4.1 | `GET /resources` | มีเครื่องครบ **และคัด id ของเครื่องแต่ละแบบเก็บไว้ใช้ต่อ** | `200` |
| 4.2 | `GET /resources/usage` | `free = total − used` ทุกแถว · ไม่มีเครื่องไหนถูกใช้เกินความจุ | `200` |
| 4.3 | ADMIN เพิ่มเครื่องใหม่ | `status` เริ่มต้นเป็น `AVAILABLE` | `201` |
| 4.4 | เพิ่มเครื่องชื่อซ้ำ | unique index ที่ `server_name` | `409 DUPLICATE` |
| 4.5 | นักศึกษาเพิ่มเครื่อง | จัดการเครื่องได้เฉพาะ ADMIN | `403` |
| 4.6 | `totalCpu: -4` | ความจุติดลบไม่มีความหมาย | `400` |
| 4.7 | `GET /resources/:id` | ได้รายละเอียดพร้อมการจัดสรรที่ยัง active | `200` |
| 4.8 | เปลี่ยน `status` เป็น `MAINTENANCE` | `PATCH` ทำงาน (และเครื่องนี้จะถูกใช้ต่อในข้อ 6.5c) | `200` |
| 4.9 | `GET /resources/999999` | ไม่พบ | `404` |

**ข้อ 4.1 ทำงานพิเศษกว่าชื่อ** — มันไม่ได้แค่เช็กว่าได้ 200 แต่ไล่หาในผลลัพธ์ว่าเครื่องไหนมี GPU
เครื่องไหนธรรมดา เครื่องไหนปิดซ่อม แล้วเก็บ id ไว้เป็นตัวแปร โฟลเดอร์ 6 จึงไม่ต้อง hardcode เลข id
ซึ่งจะพังทันทีถ้ารัน seed ใหม่แล้ว id เปลี่ยน

**ข้อ 4.2 คือหลักฐานว่าทำไมไม่เก็บคอลัมน์ "ที่เหลือ"** — มันเช็กความสัมพันธ์ `free = total − used` ทุกแถว
ถ้าเราเก็บ `used` ไว้ในตารางแทนที่จะคำนวณสด วันหนึ่งข้อนี้จะแดงเพราะตัวเลขสองที่ไม่ตรงกัน

## 5 · Requests — 25 ข้อ (โฟลเดอร์ใหญ่ที่สุด)

หัวใจของระบบ — เดินทั้งเส้นทางตั้งแต่ยื่นจนจบ ทั้งเส้นที่อนุมัติ เส้นที่ปฏิเสธ และเส้นที่ยกเลิก

### ยื่นคำขอ (5.1–5.6)

| ข้อ | ยิงอะไร | ทดสอบว่า | ต้องได้ |
|---|---|---|---|
| 5.1 | นักศึกษายื่นคำขอ | `status` เริ่มที่ `PENDING` · **`studentId` มาจาก token ไม่ใช่ body** · `rejectReason` และ `reviewedAt` ยังว่าง | `201` |
| 5.2 | ยัด `studentId: 1` + `status: "APPROVED"` มาใน body | ถูกตีตก **พร้อมบอกว่าคีย์ไหนเกิน** | `400` |
| 5.3 | `endDate` มาก่อน `startDate` | ช่วงวันที่กลับหัวไม่ได้ | `400 DATE_RANGE_INVALID` |
| 5.4 | `teacherId` ชี้ไปที่นักศึกษา | ผู้รับรองต้องเป็นอาจารย์จริง | `400 TEACHER_INVALID` |
| 5.5 | `reason` สั้นแค่ 2 ตัวอักษร | บังคับให้อธิบายเหตุผลจริง ๆ | `400` |
| 5.6 | อาจารย์ยื่นคำขอเอง | ยื่นได้เฉพาะ STUDENT | `403` |

**ข้อ 5.2 คือข้อที่สำคัญที่สุดในโฟลเดอร์นี้** — มันคือการลองยกระดับสิทธิ์ตัวเองด้วยการยัดฟิลด์
ถ้า API เงียบ ๆ ตัดคีย์เกินทิ้ง (ซึ่งเป็นค่า default ของหลาย framework) คนยิงจะเข้าใจผิดว่าค่าถูกใช้แล้ว
เราตั้ง `forbidNonWhitelisted: true` ให้มันตอบกลับมาว่า `property studentId should not exist`

> ข้อ 5.4 กติกาเดียวกันถูกบังคับซ้ำที่ชั้นฐานข้อมูลด้วย trigger `requests_enforce_roles`
> ต่อให้อ้อม API ไป `INSERT` ตรง ๆ ก็ยังไม่ผ่าน

### ใครเห็นอะไร (5.7–5.9)

| ข้อ | ยิงอะไร | ทดสอบว่า | ต้องได้ |
|---|---|---|---|
| 5.7 | นักศึกษาดูรายการ | ทุกใบที่ได้มี `studentId` เป็นตัวเอง | `200` |
| 5.8 | อาจารย์ดูรายการ | ทุกใบที่ได้มี `teacherId` เป็นตัวเอง | `200` |
| 5.9 | นักศึกษาคนที่สองเปิดคำขอของเรา | **`404` ไม่ใช่ `403`** | `404` |

**ข้อ 5.9 คือการทดสอบ IDOR** (Insecure Direct Object Reference) — ช่องโหว่ที่พบบ่อยที่สุดอย่างหนึ่ง

ทำไมต้อง `404` ไม่ใช่ `403`: `403` แปลว่า "ของชิ้นนี้มีอยู่จริง แต่คุณไม่มีสิทธิ์"
แค่นั้นก็พอให้ไล่ยิง id ทีละเลขจนรู้ว่าระบบมีคำขอเลขไหนบ้าง และมีทั้งหมดกี่ใบ
ตอบ `404` เหมือนกันหมด เขาจึงแยกไม่ออกว่า "ไม่มี" กับ "มีแต่ไม่ใช่ของคุณ"

### เส้นทางอนุมัติ (5.10–5.15)

| ข้อ | ยิงอะไร | ทดสอบว่า | ต้องได้ |
|---|---|---|---|
| 5.10 | เจ้าของแก้คำขอตอนยัง `PENDING` | แก้ได้จริงและค่าเปลี่ยน | `200` |
| 5.11 | **อาจารย์คนที่ไม่ได้ถูกระบุ** กดอนุมัติ | อนุมัติแทนกันไม่ได้ (เหตุผล `404` เดียวกับ 5.9) | `404` |
| 5.12 | นักศึกษากดอนุมัติคำขอตัวเอง | role ผิด | `403` |
| 5.13 | อาจารย์ที่ถูกระบุอนุมัติ | `status` → `APPROVED` · `reviewedAt` ถูกประทับเวลา | `200` |
| 5.14 | อนุมัติซ้ำ | state machine กันไว้ | `409 STATE_INVALID` |
| 5.15 | แก้คำขอ**หลัง**อนุมัติแล้ว | แก้ได้เฉพาะตอน `PENDING` | `409 STATE_INVALID` |

ข้อ 5.15 กันกรณีที่นักศึกษายื่นขอ CPU 4 core ให้อาจารย์อนุมัติ แล้วค่อยแอบแก้เป็น 64 core ทีหลัง

### เส้นทางปฏิเสธ (5.16–5.19)

| ข้อ | ยิงอะไร | ทดสอบว่า | ต้องได้ |
|---|---|---|---|
| 5.16 | ยื่นคำขอใบที่สอง | เตรียมของสำหรับทดสอบการปฏิเสธ | `201` |
| 5.17 | ปฏิเสธโดยไม่ใส่เหตุผล | **ปฏิเสธต้องบอกเหตุผลเสมอ** | `400` |
| 5.18 | ปฏิเสธพร้อมเหตุผล | `status` → `REJECTED` · เหตุผลถูกเก็บจริง | `200` |
| 5.19 | อนุมัติใบที่ถูกปฏิเสธไปแล้ว | `REJECTED` เป็นสถานะปลายทาง ย้อนไม่ได้ | `409` |

> ข้อ 5.17 ฐานข้อมูลบังคับซ้ำอีกชั้นด้วย `CHECK requests_reject_reason_chk`
> ซึ่งบังคับ**สองทาง** — REJECTED ต้องมีเหตุผล และไม่ REJECTED ต้องไม่มีเหตุผลค้างอยู่

### เส้นทางยกเลิก (5.20–5.23)

| ข้อ | ยิงอะไร | ทดสอบว่า | ต้องได้ |
|---|---|---|---|
| 5.20 | ยื่นคำขอใบที่สาม | เตรียมของ | `201` |
| 5.21 | นักศึกษาอีกคนกดยกเลิกใบของเรา | ยกเลิกได้เฉพาะเจ้าของ | `404` |
| 5.22 | เจ้าของกดยกเลิก | `status` → `CANCELLED` | `200` |
| 5.23 | ยกเลิกซ้ำ | สถานะปลายทาง | `409` |

### ตัวกรอง (5.24–5.25)

| ข้อ | ยิงอะไร | ต้องได้ |
|---|---|---|
| 5.24 | `?status=PENDING` | `200` · ทุกใบเป็น PENDING |
| 5.25 | `?status=WAITING` (ไม่มีใน enum) | `400` |

## 6 · Allocations — 24 ข้อ

ขั้นที่ซับซ้อนที่สุด เพราะต้องเช็ก 5 อย่างพร้อมกัน: สถานะคำขอ · สถานะเครื่อง · GPU · ความจุ · port ชน

> ข้อที่ลงท้าย **a/b** คือข้อเตรียมของ (ยื่นคำขอ + อนุมัติ) เพื่อให้ข้อ **c** มีคำขอที่ `APPROVED` ไว้ทดสอบ
> ทำเป็น request จริงแทนการเขียนสคริปต์ใน pre-request เพราะ `pm.sendRequest` ที่ซ้อน callback ไม่ถูกรอให้จบ

### สิทธิ์และเส้นทางหลัก (6.1–6.4)

| ข้อ | ยิงอะไร | ทดสอบว่า | ต้องได้ |
|---|---|---|---|
| 6.1 | นักศึกษาจัดสรรเครื่องเอง | จัดสรรได้เฉพาะ ADMIN | `403` |
| 6.2 | ADMIN จัดสรรให้คำขอที่ `APPROVED` | **คำขอเลื่อนเป็น `ALLOCATED` ในคำสั่งเดียวกัน** · `releasedAt` ยังว่าง | `201` |
| 6.3 | จัดสรรซ้ำให้คำขอเดิม | คำขอกลายเป็น `ALLOCATED` แล้ว ไม่ผ่านด่าน `APPROVED` อีก | `409` |
| 6.4 | จัดสรรให้คำขอที่ถูกยกเลิกไปแล้ว | ต้องอนุมัติก่อนเท่านั้น | `409` |

**ข้อ 6.2 เช็กสิ่งที่มองไม่เห็น** — มันตรวจว่า `request.status` ที่ติดกลับมาเป็น `ALLOCATED` แล้ว
ไม่ใช่ `APPROVED` ข้อนี้เคยแดงจริงตอนพัฒนา เพราะใน transaction สร้าง allocation ก่อนอัปเดตคำขอ
ค่าที่ `include` กลับมาจึงเป็นภาพเก่า แก้โดยสลับลำดับ

### เงื่อนไขการจัดสรร (6.5–6.11)

| ข้อ | ยิงอะไร | ทดสอบว่า | ต้องได้ |
|---|---|---|---|
| 6.5c | จัดลงเครื่องที่ `MAINTENANCE` | เครื่องปิดซ่อมรับงานไม่ได้ | `409 RESOURCE_UNAVAILABLE` |
| 6.6 | `ipAddress: "999.1.1.1"` | รูปแบบ IP ถูกตรวจ | `400` |
| 6.7 | `port: 70000` | port เกินช่วง 1–65535 | `400` |
| 6.8 | port ชนกับที่ยังใช้อยู่ **บนเครื่องเดียวกัน** | partial unique index ที่ชั้น DB | `409` |
| 6.9c | คำขอที่ขอ GPU จัดลงเครื่องที่ไม่มี GPU | จับคู่ความต้องการกับสเปกเครื่อง | `409 GPU_REQUIRED` |
| 6.10 | คำขอเดียวกันจัดลงเครื่องที่**มี** GPU | ผ่าน และลงเครื่องที่ `hasGpu = true` จริง | `201` |
| 6.11c | คำขอที่ขอ CPU 256 core ลงเครื่อง 16 core | รวมของเดิม + ของใหม่ แล้วเทียบกับความจุ | `409 CAPACITY_EXCEEDED` |

ข้อ 6.9c กับ 6.10 เป็นคู่กัน — พิสูจน์ว่ากติกา**กันเฉพาะกรณีที่ควรกัน** ไม่ได้กันมั่วไปหมด
ชุดทดสอบที่มีแต่ข้อ 6.9c อย่างเดียว จะผ่านแม้โค้ดจะปฏิเสธการจัดสรร GPU ทุกกรณี

### การมองเห็น (6.12–6.14)

| ข้อ | ยิงอะไร | ต้องได้ |
|---|---|---|
| 6.12 | ADMIN ดูรายการทั้งหมด | `200` |
| 6.13 | `?active=true` | `200` · ทุกรายการ `releasedAt` เป็น `null` |
| 6.14 | นักศึกษาคนที่สองดูรายการ | `200` · ไม่เห็นของคนอื่น |

### คืนเครื่อง (6.15–6.18)

| ข้อ | ยิงอะไร | ทดสอบว่า | ต้องได้ |
|---|---|---|---|
| 6.15 | คืนเครื่อง | `releasedAt` ถูกประทับ · **แถวยังอยู่ ไม่ได้ถูกลบ** · คำขอเลื่อนเป็น `EXPIRED` | `200` |
| 6.16 | คืนซ้ำ | คืนไปแล้วคืนอีกไม่ได้ | `409 ALREADY_RELEASED` |
| 6.17 | ใช้ **port เดิม** ซ้ำหลังคืนแล้ว | **ผ่าน** | `201` |
| 6.18 | คืนรายการ id `999999` | ไม่พบ | `404` |

**6.8 กับ 6.17 คือคู่ที่อธิบาย partial unique index ได้ดีที่สุด**

```sql
CREATE UNIQUE INDEX allocations_active_port_uniq
  ON allocations (resource_id, port)
  WHERE released_at IS NULL;    -- ← ท่อนนี้คือทั้งหมด
```

- **6.8** port ซ้ำตอนยังใช้อยู่ → `409` (ถูกต้อง สองคนใช้ port เดียวกันไม่ได้)
- **6.17** port ซ้ำหลังคืนแล้ว → `201` (ถูกต้อง port ที่ว่างแล้วต้องเอากลับมาใช้ได้)

ถ้าเป็น unique index ธรรมดาที่ไม่มี `WHERE` ข้อ 6.17 จะแดง เพราะ port ที่เคยใช้จะใช้ซ้ำไม่ได้ตลอดกาล
มี 6.8 อย่างเดียวจะจับ bug นี้ไม่ได้เลย

**ข้อ 6.15 ตรวจว่าแถวยังอยู่** — คืนเครื่องคือประทับ `releasedAt` ไม่ใช่ `DELETE`
ถ้าลบทิ้ง port จะว่างเหมือนกัน แต่ประวัติว่าใครเคยใช้เครื่องไหนจะหายไปด้วย

## 7 · Audit logs — 5 ข้อ

| ข้อ | ยิงอะไร | ทดสอบว่า | ต้องได้ |
|---|---|---|---|
| 7.1 | ADMIN อ่าน log | มีบันทึกอยู่ · เรียงใหม่สุดขึ้นก่อน | `200` |
| 7.2 | นักศึกษาอ่าน log | อ่านได้เฉพาะ ADMIN | `403` |
| 7.3 | `?action=ALLOCATION_CREATE` | **การจัดสรรในโฟลเดอร์ 6 ถูกบันทึกจริง** | `200` |
| 7.4 | `?action=REQUEST_APPROVE` | **การอนุมัติในโฟลเดอร์ 5 ถูกบันทึกจริง** | `200` |
| 7.5 | `?limit=5000` | จำกัดสูงสุด 100 ต่อหน้า | `400` |

7.3 กับ 7.4 ไม่ได้ทดสอบ endpoint นี้เป็นหลัก แต่**ย้อนกลับไปตรวจว่าโฟลเดอร์ก่อนหน้าเขียน log จริง**
ถ้า `AuditService.log()` พังเงียบ ๆ สองข้อนี้จะแดง ทั้งที่การอนุมัติกับจัดสรรผ่านหมด

> ตาราง `audit_logs` เขียนได้อย่างเดียว — `UPDATE`/`DELETE` ถูก trigger ปฏิเสธ
> ทดสอบเรื่องนี้ที่ `scripts/db-rules-check.sql` ข้อ 7–8 เพราะ API ไม่มี endpoint ให้แก้อยู่แล้ว

## 8 · เก็บกวาดหลังทดสอบ — 5 ข้อ

ทำให้ชุดทดสอบ **รันซ้ำได้ไม่จำกัด** โดยไม่ทิ้งขยะสะสม

| ข้อ | ทำอะไร |
|---|---|
| 8.1 | คืนเครื่อง GPU ที่จองไว้ตอนทดสอบ |
| 8.2 | คืนเครื่องที่ใช้ port ซ้ำ |
| 8.3 | ลบ TEACHER ที่สร้างในข้อ 3.6 |
| 8.4 | ลบเครื่องที่สร้างในข้อ 4.3 |
| 8.5 | **ตรวจว่าไม่มีเครื่องไหน `free_*` ติดลบ** หลังรันครบทั้ง 96 ข้อ |

**ข้อ 8.5 คือข้อที่มีค่าที่สุดในโฟลเดอร์นี้** — มันไม่ได้ทดสอบ endpoint ใดเป็นพิเศษ
แต่ตรวจว่าหลังจากยิงมาทั้งชุด — จัดสรร คืน จัดซ้ำ ยกเลิก ปฏิเสธ — **ฐานข้อมูลยังอยู่ในสถานะที่สมเหตุสมผล**

ทรัพยากรคงเหลือติดลบแปลว่ามีการจัดสรรที่หลุดการตรวจไปได้ ซึ่งข้อทดสอบรายข้ออาจจับไม่ได้
เพราะแต่ละข้อดูแค่ response ของตัวเอง ไม่ได้ดูภาพรวม
